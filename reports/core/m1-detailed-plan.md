### P1 文本模型（3 个 PR）

目标：一个 Task 能调用真实的 OpenAI 兼容模型，模型能提出工具调用，Tool Loop 把它们按顺序执行。

**PR 1：工具调用的 Core 接口（MA-008C 前半，ABI 0.37）**

- 按你的选择，工具调用以 typed 结构进入 Core。调用结果新增一种格式：最终文本，或一个有界的工具调用列表（至多 8 项），每项是 Binding、具体 Scope 参数和可选正文。
- 请求一侧新增工具视图：Kernel 把可用工具的字段类型、单位、取值域交给 Provider，Provider 据此向模型描述工具，并把模型给的 JSON 参数解码成 typed 值；解码不了的报分类错误，策略看不到原始 JSON。
- 按你的选择，工具范围由 GoalType 声明允许列表（Binding ID 与版本），Kernel 取其中该 Task 已有授权的部分。模型提出的每个调用仍走原有的 Binding、授权、资源与屏障校验。
- 工具调用列表随调用结果持久（调用记录兼容扩展，schema 2 不变）；Mock A/B 增加确定性的工具调用输出，供测试和没有密钥时使用。

**PR 2：OpenAI 兼容 Provider（MA-008C 后半，****`providers/openai_compat/`****）**

- Core 之外的组件，只依赖公开头文件；一个工作线程跑 libcurl multi，yyjson 做有界解析（字节、深度 8、数组长度都有上限），结果经 `ayni_provider_post` 投递。
- 非流式 Chat Completions，文本与函数工具调用；不自动重试、不自动换服务（ADR-0042 #4）。调用属性声明外发与计费副作用、不支持查询；取消 HTTP 报 `CANCEL_UNKNOWN`，因为中断连接不能证明远端未执行。
- base URL、model、密钥所在的环境变量名在运行时配置；密钥只由 Provider 读取，不进 Core、日志或提交。
- 本地协议夹具：测试里起一个回环 HTTP 服务，回放正常、工具调用、各类 HTTP 错误、畸形与超长 JSON、超时；CI 不联网。CI 镜像需要加 libcurl 开发包，yyjson 固定版本引入。
- 实 API 验证单独做，用哪家服务、密钥怎么给在 PR 2 开工前问你。

**PR 3：规则策略与 Tool Loop（MA-009，****`strategies/`****）**

- 两个策略都是 Core 之外的组件，只用公开的 `ayni_register_strategy`，不改 Kernel 业务分支。
- 规则策略：启动时配置的有限规则表，每条规则是一串命名、带版本的步骤，参数固定；给 Agent A 和之后的提醒、设备检查用。
- Tool Loop：一轮是一次模型调用；结果是工具调用列表时，按顺序一次决定发一个（Kernel 现有规则），全部完成后进入下一轮。步骤名由轮次与序号导出，重启或换策略后不变。任一结果未知就停住后续步骤并报原因；补救动作是新调用、重新授权，不自动发。轮数受 Task 模型调用上限（默认 8）约束。
- 私有检查点带版本；策略声明能接受的检查点版本，不兼容时 Task 停住并报原因，不重置（E3 步骤 5）。是否需要在策略注册里加兼容版本范围，开工时按现有 ADR-0024/0026 的规则定。
- 多轮对话按你选的“模型摘要旧轮次”：一个有界的对话记录保存最近几轮正文和一份摘要；超过上限时，这一轮的 Task 先发一次摘要模型调用，计入该 Task 的模型次数，写入成功后才丢弃被摘要的旧轮次。摘要是模型推断，只在本对话内使用，不进记忆、不算确认事实，并记下它来自哪些轮次。P1 只支持删除整个对话（正文与摘要一起清除）；删除单轮后让摘要失效、按仍有效的轮次重新生成，等 P3 的 tombstone 与 lineage 机制一起做。上限的具体轮数与字节开工时按内存量测定。
- **验收（P1 整体）**：Mock 驱动的两步工具链、未知结果阻断、达到模型次数上限暂停、允许列表外的工具被拒、不兼容检查点停住、重启后换策略继续；夹具覆盖协议正常与错误路径。内存按 ABI 变化重量。

### P2 第一次能用（1–2 个 PR，MA-020 前半）

目标：你在电脑上启动一个程序，就能和 Agent A（规则）、Agent B（Tool Loop）对话，退出再开接着用。

- **Native CLI（按你的选择做单进程）**：交互式命令行内嵌 Kernel，后台线程推进 `ayni_step`；本机用户即所有者，CLI 启动时以可信 Host 建立所有者会话。命令覆盖：对 A/B 说话、列出 Goal/Task/调用、创建与撤销 Grant、批准待批目标、提高模型次数上限、恢复等待、查询未知结果、状态、退出。全部映射到已有的意图，不开旁路。

- **验收**：CI 里用 Mock 跑脚本化的 CLI 会话（含退出重开后继续）；真实模型的会话由你在本机试用。
- **开工选择（用户 2026-10-26）**：英文短命令配中文提示；配置 `~/.config/ayni/`、数据 `~/.local/share/ayni/`，支持 XDG 与显式覆盖，密钥只从环境读取。按两个 PR 交付 runtime/文件与 CLI/脚本会话（ADR-0057）。

### P3 结构与记忆（2–3 个 PR）

目标：在新增持久实体之前收紧 kernel 结构；然后让 Agent 有私有记忆，所有者有公共档案。

**PR 1：结构整改（F01、F14、F08，已合并 #79）**

- **F01**：`ayni_kernel` 的成员私有化，经 facade 访问；kernel 内分成 service（意图、调用、执行、授权的领域编排）和 runtime（step 循环、ingress、完成槽、存储维护）两个分区，依赖只从 runtime 指向 service，写进 `tools/architecture.json` 由机器检查；`WorkModel` 移出 `kernel/intent/`。
- **F14**：#70 只做了 `IntentContext`。补上 `StepContext`，把当前时间、工作项预算、报告截止时间显式传递，去掉哨兵默认值。
- **F08**：回调重入保护从 `WorkModel` 的裸布尔改为 API 闸门持有的作用域守卫。
- 行为、ABI、schema 不变；一次审查看不过来就拆成“成员私有化”与“分区、StepContext 与守卫”两个 PR。

**PR 2：授权与持久化前置整改（F12、F04 的 Grant/命令部分，ADR-0059）**

- GrantTable 保持事实，独立 RevocationGate 持有已接受拒绝，GrantRestore 负责历史验证与恢复。
- Grant 记录族及 command 迁入既有 PersistentStore，保持原字节格式、顺序、REQUIRED 规则和跨记录配对。
- 为使完整记忆/删除审查聚焦其语义，将这项兼容整改独立交付；总数仍为三个 PR。

**PR 3：私有记忆与公共档案（MA-011A，`core/knowledge/memory/`）**

- 记录：ID 与版本、命名空间（某个 Agent 实例私有，或所有者公共档案）、来源（用户陈述、模型推断、整理派生）、确认状态、有界的标签与关键词、有界正文、有界的派生 lineage。表满拒绝新写入并保留已有数据（ADR-0042 #5）。
- 访问：Agent 默认只读写自己的私有命名空间；公共档案按 Agent 授权读、写、用途与期限；把私有记录共享给另一个 Agent 是显式授权，撤销后立即不进入新查询和上下文。
- 检索：关键词与标签匹配，返回有界的前 K 条；策略组上下文时记下用到的记录 ID 与版本，进入调用输入的 lineage。
- 删除：先 tombstone，记录立即不可检索、不进新上下文，在途依赖它的结果在应用时按 tombstone、`expected_revision` 与授权版本拒绝；再由可跨重启继续的有界清理擦除正文。日志与快照里的旧正文靠快照轮转覆盖，每步清理有界，完成还等待文件/借用及双槽轮转，不承诺固定墙钟时限。P1 留下的“删除单轮对话使摘要失效并重新生成”也在这里接上。
- 所有者命令：查看、修改、删除、确认记忆；敏感删除只接受所有者会话。
- **随同处理**：复用前置 PR 的 F04 Grant/命令适配与 F12 撤销闸门；F10 从这里起，新注册入口在 `kernel/api` 解码后再交给领域模块，已有的注册在被改到时迁移。
- **验收**：E1 步骤 1、7、9 的正常路径（私有拒读、共享与撤销、档案只授权 A、删除后旧结果不复活）；单轮对话删除后摘要失效并重新生成。
- **用户已定（2026-10-26）**：显式管理保存即确认，模型/派生结果待所有者确认；整个 Kernel 默认 64 条、正文 512 UTF-8 字节、每条 8 项依赖，启动可配置；公共档案初始为空，只收显式基础偏好且各 Agent 单独授权；写经 Kernel 意图，读经受限查询和策略视图。

### P4 时间与订阅（2–3 个 PR）

目标：提醒能按日历触发；传感数据能从任意线程进入 Core，并按订阅代际管理。

**PR 1：可信 UTC 与日历（MA-011B）**

- Host 新增 UTC 端口并报告可信等级（Native 用系统时钟并报告是否已校时，sim Host 可注入跳变）。UTC 与单调时钟独立，UTC 跳变不影响已有的单调计时。
- 日历触发：单次、每日、每周；occurrence 的稳定身份取计划时刻，而不是计数器。
- 时间不可信时日历目标等待“待校时”。断电、恢复或待校时期间错过的提醒，恢复后补发一次并标原定时间，周期提醒错过多次也只补一次（C-PROD-018，已定）。夏令时跳过的时刻在下一个有效时刻触发一次，重复的一小时只触发一次。
- 持久：Goal 触发记录新增日历规则与最后触发游标，按 `PersistentStore` 契约写。

**PR 2–3：观测队列/媒体引用与 Task 订阅（MA-008B）**

- 订阅调用形态：`STARTING → ACTIVE → STOPPING → STOPPED`，另有 `EXPIRED`、`FAILED`。Provider 确认开始前不接纳观测（C-SUB-001）；每次开启或重启是新代际，事件按订阅、代际、序号校验，旧代际不进新上下文（C-SUB-002）；续租重查授权与运行限制，失败即停新采集（C-SUB-003）。
- 观测队列（ADR-0052 决策 6，已定）：任意非 ISR 线程把样本投进有界队列，满了拒绝并计数、不阻塞生产者；拥有者线程按现有规则写入 `ObservationTable`。
- gap：每类事件声明可合并、可丢弃与 gap 行为（C-SUB-004）；遥测出现 gap 时计数，依赖它的条件视为过期，直到新样本到达。
- 媒体引用：Core 只保存引用元数据（所有者、用途、有效期、大小、内容类型、代际），字节由 Host 的媒体存储持有（Native 用 Mock）；过期、取消、重启时回收，不持久原始媒体。
- 新代际触发依赖复核：Scene 前提与观察目标依赖的样本在代际变化时失效；订阅开启与关闭的回执走可靠完成槽。
- **随同处理**：F10 的观测源注册把版本与 `struct_size` 检查移到 `kernel/api`（`observation_api.cpp` 的 `decode_source` 已是这种写法，订阅源照此写）；订阅与日历的新记录从一开始就按 F04 的存储契约写。
- **验收**：E1 步骤 3、8 与 E4 步骤 4 的正常路径（共享摄像头订阅、关闭后旧代尾部不进上下文、重开用新代际）；日历的每日/每周、待校时与补发一次。
- **用户已定（2026-10-27）**：Task 所有、共享通过资源容量；POSIX TZ 含夏令时；M1 元数据加 Mock 字节。默认30秒、半租期 Kernel 重查授权/运行限制自动续租；正常重启或暂停恢复原 Task 以新代际重开；ACTIVE 后 Task 可继续分析，分析完成后等待新样本或订阅状态、忙时只用最新值。ADR-0061/0062/0063 分别记录日历、传输与订阅决定。
- **交付边界**：#82 日历、#83 任意线程观测/媒体，最后的订阅 PR 复用调用/资源/可靠控制，新增 Task WAITING 前沿。WAITING 的持久状态属于 Task，订阅记录仍由 Call 的 PersistentStore 处理；不为等待另建调度器。

### P5 统一助理与 SDK（2–3 个 PR）

目标：一个助理入口管理两个 Agent 和四类目标；第三方只用公开 API 就能接入。

**交付拆分（2026-10-27）：** P5 先以独立 PR 完成 F04 的 Agent/Goal/Task 存储职责迁移（ADR-0064），随后以独立 API 能力交付通用持久暂停组，再交付统一助理与通知，最后交付 SDK 与示例。多记录快照游标迁移和通用暂停组各有独立交付边界；将其与应用协调策略分开审查，避免持久/授权变更被应用改动掩盖。P5 因此按四个完整能力 PR 交付。

**PR 1：统一助理与通知（MA-019）**

- 助理协调器是 Core 之外的可信应用组件：会话意图路由、重复或冲突建议合并、公共档案授权请求、多 Agent 回复汇合；Kernel 仍是目标、权限与执行事实的权威。
- 暂停助理（ADR-0042 #5，已定）：Core 提供通用的持久暂停组，可信应用在创建 Goal 时决定归属；暂停期间新建的自主工作同样受限；提醒与显式用户工作不在组内；紧急停止单独显示与恢复。
- 四类目标：提醒（日历触发，`notify.present` 成功才完成，失败或未知待处理，安静时段延后）；设备检查（周期，只用获准检查能力，Mock 设备健康）；记忆整理（空闲、低优先级，生成未确认的摘要与重复候选，带 lineage）；场景观察（订阅驱动的变化触发加周期抽查，Mock 摄像头源）。
- 通知：渠道呈现是声明“通知”副作用的能力调用；CLI 呈现器写出成功即呈现证据；用户可见状态由调用事实投影（AVAILABLE、PRESENTING、PRESENTED、PRESENTATION_UNKNOWN/FAILED）。
- 助理状态投影（正在处理、后台观察、等待授权、已暂停、离线、需要处理）在 CLI 显示，内部 ID 只在诊断命令里。
- **随同处理**：F04 把 Goal、Task、Agent 存储迁到 `PersistentStore` 契约，因为暂停组和新目标类型都要改这三张表的记录。至此 F04 完成。
- **验收**：E1 步骤 11 与 E4 步骤 7 的正常路径（暂停保留提醒、只有成功呈现才完成、重启不重播已确认通知）。
- **用户已定（2026-10-27）：** 文本点名优先，未点名按简单规则路由；实现安静时段机制但默认关闭；自主工作暂停期间不补积压；每个 Goal 单组归属，子 Goal 同时受祖先组限制。提醒与显式用户工作不加入助理自主暂停组。

**PR 2：C++ 封装与接入示例（MA-020 后半）**

- `include/ayni/ayni.hpp`：C++17 RAII 封装，无异常与 RTTI，显式状态返回，不跨 ABI 暴露 STL；显式排空与关闭辅助。
- `examples/` 里四个只用公开 API 的示例：新硬件（触觉按钮订阅）、新模型（第二个 OpenAI 兼容 Provider）、新策略（事件规则）、组合工作流（E4 的 `composite_workflow`）。CI 编译并运行；另配双 Agent 演示脚本。
