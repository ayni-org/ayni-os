# Ayni AgentOS 基础通用能力实施与平台实验计划

- **状态**：用户 2026-10-29 明确定位与先后顺序；AP-02/AP-03 已交付，2026-10-30 完成 AP-05 软件实现、正常验证及独立复审（ADR-0086、#116）。容量和后续包选择仍分别决定；平台或硬件实验仍另行安排。
- **依据**：[ADR-0083](../adr/0083-general-foundation-before-platform-experiments.md)、[主计划](../ayni_v1.0.md)、[能力契约设计](capability-centered-agentos-plan.md)、[发现与适配细化](capability-discovery-and-adapters.md)。
- **当前实现**：[#116](https://github.com/RobotSe7en/ayni/pull/116)；实验性 ABI 0.52 / schema 8 正在本包验收，见 [AP-06/AP-04 设计](ap06-ap04-foundation-design.md)和[基础报告](../../reports/core/foundation-acceptance.md)。AP-00/AP-01/AP-02 及 AP-03 目录、按需绑定和 Native harness 的实现/验证记录见关联 PR；基础通用能力尚未整体完成，平台实验尚未启动。
- **规划归属**：本文统一规定当前实施范围、依赖、完成条件和实验次序。AP/MA 编号继续用于追踪；历史 M0/M1 与已交付报告保留其事实，不再从原 M2～M6 轮式产品顺序推导通用 AgentOS 的必需功能。

## 1 目标与边界

Ayni 提供通用原生 AgentOS：同一 Core 管理 Agent、Goal、Task、调用、授权、资源、记忆/上下文及持久恢复，能力提供者通过公开契约接入宿主的设备、软件或服务。宿主只须满足所选系统配置的 Host 契约，不要求摄像头、麦克风、扬声器、电机、屏幕或物理设备树。仅有软件能力也是有效部署。

顺序为：**先完成并验收基础通用能力，再安排 ESP32-S3、Linux 系统等平台实验，最后按实际需求扩展具体能力和协议。** ESP32-S3 与 Linux 不互为前置，具体先后和实验组合在进入实验阶段时安排。基础开发继续使用现有 Linux Native/Sim 构建、夹具和 CI；这些开发验证不同于后续实际 OS 服务集成、设备及平台资源实验。

语音、视觉、运动、机器人、MCP/ROS/MHS 和 peer 均按能力或适配扩展选择，不构成所有宿主的安装条件。通用取消、超时、撤权、关闭和未知副作用处理仍须实现；物理执行能力另履行现有许可、联锁、停止确认及硬件失能契约。未启用物理执行不要求装配电机停止链；启用后不得降低其保证。

## 3 基础通用能力实施包

下表是当前基础阶段的范围；实现细节沿用能力架构计划，不另造一套运行时、权限目录或恢复账本。

| 工作包 | 实施内容与属主 | 依赖与交付边界 | 可判定的完成条件 |
|---|---|---|---|
| 基线盘点 | 对照公开契约、追踪矩阵及当前消费者核对上述机制和缺口 | 在首个新实现包前完成；缺口归回现有模块 | 列出需要修改的 API、Provider、模型 codec、策略、SDK、记录 reader/writer 与 runtime；保留已有证据和未验证范围 |
| **AP-02：业务输入与结果** | catalog 拥有有界类型定义，authority 拥有授权域，work 拥有规范请求与结果生命周期；扩展定义业务语义，模型 Provider 只编解码 | AP-01；D04/D07 本包范围已定，盘点、类型、授权及迁移细节见 [AP-02 设计](ap02-typed-capability-design.md) | 模型 JSON 与原生输入走同一语义校验；默认值在授权前确定；授权、持久接受与执行消费同一规范请求；结果结构、错误、容量及版本明确 |
| **AP-03：注册、发现与工具视图** | 外部 backend 产生候选；可信配置采纳；catalog/authority 决定目录和披露，模型请求只借用有界视图 | AP-01；使用新输入时依赖 AP-02；先决定 D03 可见权限、D05 目录/窗口预算 | 候选不自动授信；配置期注册/启动冻结保持；目录不受旧八项业务工具窗口限制；固定原生工具和按需分页、失效 cursor、撤权与说明读取有确定结果，不因发现扩大权限 |
| **AP-04：多实例验证与必要演进** | 检查能力定义、Provider 实现、Binding、资源和历史 Call 的归属 | 在基础验收前用两个纯软件实例或模拟端点验证；只有现机制不能满足场景时，才按 D06/D07 独立演进 | 同语义两个实例可精确选择，资源占用按声明关联，已接受调用不暗换实例；若保持现契约可完成，记录证据而不强造新接口 |
| **AP-05：长操作与订阅控制** | work 保有 Task 所属操作引用和订阅；策略提出启动/读取/等待/取消/关闭；Provider 异步执行 | AP-02；D09 已定，消费者与接口设计见 [AP-05 设计](ap05-managed-operations-design.md)、ADR-0086，ABI0.51/schema7，正常软件/SDK验证与独立复审见 #116 | 以可取消的软件长任务、事件流验证接受/进度/终态、租期/代际、等待/关闭、背压及晚到结果；不靠普通 Provider 回调 Core 建立旁路 |
| **AP-06：SDK、扩展和应用复用** | 公开 C/C++ 接入；共用应用行为归 applications，Host/Provider 各管端口与资源，runtime 唯一装配 | AP-01 后可独立推进；在基础验收前适配最终接口 | 能力定义、说明、实现及部署配置足以接入软件能力；一般新增能力无需 Core 或模型 codec 业务分支；Native/Sim 共用应用编排，助理只作应用样例 |
| 基础收尾 | 同步 ABI/存储/契约、示例与文档，汇总适用回归和证据 | 以上各包完成及接口迁移完毕 | 通过第 5 节基础门槛后，才进入第 6 节平台实验 |

用户 2026-10-29 已选择 AP-02 首版同时支持有界对象、列表、嵌套、浮点与精确十进制，连同整数、布尔、枚举/标识符和 UTF-8 文本；不要求完整 JSON Schema 或新的线协议。列表逐项由同一完整授权覆盖，越界或空授权列表整次拒绝，关联/跨列表/总量规则后续另定；权限比较只用整数/精确十进制。本包直接升级消费者，拒旧保留目录，无旧 reader/迁移器。证据、边界和实施设计见 [ADR-0084](../adr/0084-typed-capability-values-and-authority-projection.md)与 [AP-02 设计](ap02-typed-capability-design.md)；该兼容决定不自动延续到未来包。

推荐交付顺序：基线盘点 → AP-02 → AP-03 → AP-05 → AP-06 → 基础收尾。AP-06 可提前做与新接口无关的共用边界；AP-04 的场景分析随接口设计开展，必要演进在其消费者验收前完成。各包按完整功能组织 PR，以实际依赖决定拆分，不按表格机械拆提交。

## 4 基础阶段的验证组合

| 场景 | 验证问题 | 所用环境与证据边界 |
|---|---|---|
| 纯软件能力接入 | 定义、说明、授权、绑定、真实结果能否贯通公开 API 和 ToolLoop | 本地确定性软件 Provider 与 HTTP 模型协议夹具；无需外网、付费模型或外设 |
| 多 Agent 与能力实例 | 工作隔离、权限、资源公平和实例选择是否由同一 Core 管理 | Native/Sim 中多个 Agent 和两个软件实例；不以模拟结果声明硬件支持 |
| typed 输入/结果及目录 | 默认值、未知字段、大小边界、结果解释、分页、工具窗口和披露是否一致 | 模型 codec、原生 C/C++ 消费者及公开行为场景；具体边界随接口决定 |
| 长任务与事件流 | 操作引用、等待、取消、订阅续租/代际和正常关闭是否闭环 | 软件后台工作与可控事件源；不用摄像头或电机作为必要夹具 |
| 生命周期与持久事实 | 变化是否保持幂等、派发屏障、UNKNOWN、检查点及依赖失效保证 | 保留并运行现有相关 E1～E4/专项回归；新增专项按工作流另行安排 |
| 扩展与应用复用 | 新能力是否只需扩展和配置；助理行为是否保留在应用层 | SDK 示例、Native/Sim 共用应用，按实际接口版本编译运行 |

每包执行相关正常与公开输入边界测试、设计自查、适用独立审查和最终 CI；本地检查按影响选择。新增故障/恢复和变异专项仍按[工作流](../workflow.md)的现行授权执行，不因本计划恢复。未取得的必要证据列为未验证，不能将暂停专项理解为已通过；需要补充的证据先明确范围，再安排工作。

## 5 基础通用能力完成条件

1. 生命周期、调度、授权、资源、调用、持久、记忆/上下文的公开机制与 AP-02～AP-06 所需能力有实现和对应证据，状态与错误可查询，容量和所有权明确。AP-04 可以结论为现契约已满足，无需演进。
2. 一组纯软件能力能够通过公开路径注册、被允许的主体发现和理解、被 Agent 调用、返回结构化结果，并完成长操作和事件订阅；缺少特定设备不阻断该组合。
3. 接入或更换普通能力实现不要求修改 Core、通用 ToolLoop 或模型厂商 codec 的业务分支。改变系统语义的需求按契约演进处理，不承诺永不修改 Core。
4. 新 ABI、能力版本及持久格式分别明确，所有受影响消费者迁移完成；原调用的身份、绑定、规范输入和未知结果不被新目录重释。兼容和回退决定有相应 ADR。
5. 相关检查、现有完整 CI 和适用审查通过；通用覆盖目标为 Core ≥75%、安全关键分支 ≥80%（用户 2026-10-30 统一调整，ADR-0088），低于现行门槛时须有证据及适用 ADR。统计范围与方法保持，历史测量不重写。
6. 交付基础能力报告、可复现配置、SDK/扩展示例、支持范围与未验证事项。启用范围内尚缺的必要验证不能写成通过；可选平台、协议或设备未实现不阻断基础完成。

“基础完成”不宣称所有平台已验证，也不要求所有可选能力都实现。已有 M1 报告证明其冻结版本的结果，本阶段须按最终变化汇总证据。

## 6 基础完成后的平台实验

### 6.1 共同进入条件与方法

基础阶段通过上述门槛后，再为所选平台冻结实际 Host、能力组合、容量、工具链、观察指标和成功条件。实验仅装配声明的能力：先验证系统端口与公开接入，再按需要增添设备。一个平台失败由该实验记录和处理，不把另一个平台的设备或 ROS 验收设为前置。

实验保留 E1～E4 的通用语义要求，按当前授权安排平台复核；尚未运行的恢复专项明确记未验证。无相关物理设备时可用已声明的测试 Provider 验通用流程，不能据此声称真实设备通过。基础中的既有 Native/Sim 测试继续运行，不需要为“实验后置”停止开发验证。

### 6.2 平台组合、步骤与通过证据

| 实验 | 验证问题与最小组合 | 实施步骤 | 通过证据与边界 |
|---|---|---|---|
| **ESP32-S3（AP-07；原 MA-007/024 对应实验部分）** | 受限 MCU 上同一 Core、异步 Host 与原生能力接入；先用软件计算、定时工作或测试输出 | 核对实际板型/容量；实现并验证时钟、唤醒、同步及异步存储；按实测预算配置 arena/栈/队列；接入选择的 Provider/应用并验证运行和关闭 | 锁定配置/工具链、启动与任务轨迹、内存/栈/延迟、存储日志/快照写入量、正常取消/关闭及已执行的契约复核；仅编译或 LED 演示不等于全部平台验收 |
| **Linux 系统（AP-11a 的首个平台实验；原 MA-013 相应工作）** | 已有 Native 基础在实际 OS 服务、权限、进程生命周期及真实软件后端下能否使用 | 固定发行版/ISA/用户权限及启动方式；选择受限目录文件服务、可取消软件任务或 OS 事件源；复用公开 SDK/Host/Provider，验证启动、并发、拒绝和退出清理 | 可复现安装/运行配置，实际 OS 权限和错误证据、任务/调用轨迹及资源释放；不以当前单测/CI 直接替代系统实验，不要求 root、systemd、摄像头、ROS 或 ESP32 |
| **其他系统/ISA（AP-11a 后续分项）** | Host 可移植性、平台权限和能力提供方式 | 选择可获得 SDK/设备的平台；先满足 Host 契约，再接同一组软件能力和共同用例 | 分别报告可构建、可启动、功能通过、长稳通过；手机后台等行为按实际 OS 限制验证，不从交叉编译推定支持 |

ESP32-S3 与 Linux 实验均使用同一 Core 和能力契约；差异归 Host、能力实现、容量及 runtime。跨平台支持声明需至少两个实际宿主的相应共同契约证据，不把两种模拟配置当作两个真实宿主。

各实验结束形成独立报告；不预设具体报告文件已存在。记录代码、ABI/schema/能力版本、OS/SDK/ISA、实际设备或软件后端、容量、步骤、结果及限制。硬件、恢复和耐久未执行的分别标明，不互相替代。

### 6.3 按需增加的实验与扩展

| 项目 | 何时安排 | 专属验收边界 |
|---|---|---|
| 语音/视觉与媒体（AP-08） | 选定平台确有这类能力需求时 | 真实输入输出、媒体保留/释放、格式、用途与外发权限；不要求所有宿主提供 |
| 运动与硬件停止（AP-09） | 选定实际执行器及明确硬件操作安排后 | 原许可、包络、联锁、校准、物理停止和结果验证全部适用；基础报告及 Mock 不替代 |
| MCP/ROS/MHS（AP-10） | 基础稳定且有对应互操作需求和可用规范/环境时 | 支持版本/子集、导入或导出、身份与生命周期、相关 R1；Linux 基础实验不依赖 ROS，MHS 条件不足保持未实现 |
| peer 与多节点（AP-11b、完整 MA-038） | 明确选择跨节点能力需求时 | 独立决定线协议，验证身份、授权、去重、查询、断连及固定 owner；不作为单宿主基础的前提 |
| 轮式助理、网页、OTA、ToC 试用与长稳 | 另行选择具体应用/设备发布组合后 | 原硬件、真实 OTA/回滚、72h 或用户试用等门槛约束相应支持/发布声明，不绑定 Ayni 所有部署或版本 |

## 7 决策、授权和当前下一步

已确定：通用原生 AgentOS 定位、无必备设备集合、基础先于平台实验、本机能力优先而远程可选，以及 ADR-0084/0085 的 AP-02/AP-03 选择。AP-05 的固定工具内受管控制、直接升级和最终答复收尾由用户 2026-10-30 确认（ADR-0086）；其他包的容量、绑定、兼容及控制语义仍分别决定。平台组合、具体数值指标、设备/费用、外发和物理操作在对应实施前明确。

需要决策的事项先记录在文件中，下面列出执行前的检查点。具体接口方案以[能力计划第 14 节](capability-centered-agentos-plan.md#14-待用户决策)及包内 ADR 为准；此表不把建议记为已选。

| 事项 | 选项与建议 | 影响与最晚时点 | 当前状态 |
|---|---|---|---|
| D04 首版业务类型 | 有界嵌套/列表，同时支持近似浮点与精确十进制；默认值在授权前规范化 | 具体 Schema、数值及授权边界见 AP-02 设计 | 已定（用户 2026-10-29）；AP-02 本包实现，验证见 ADR-0084 |
