# ADR-0004：跨设备身份、新鲜度与幂等

- **状态**：已接受（设计基线，待实现与验证）
- **日期**：2026-10-18
- **关联**：计划 §3.1、§3.4、§2.7；`MA-038`、`MA-016`；E2 F9

## 背景

消息分类已经清楚，但身份与重试语义仍有缺口：mTLS 只证明节点身份，不证明它可以代表所有者或某个 Agent；相对 deadline 不证明首次到达的新鲜度，滞留的命令首次到达时不应重新获得完整执行窗口；单一 `operation_id` 只是键名，不是完整的幂等契约。v1.3 的示例还在同一条 `capability.invoke` 中同时携带 `command_id` 与 `operation_id` 两套幂等键，冲突时无法判定以哪个为准。Protobuf 等序列化不是规范化表示，不能对序列化字节取哈希作为参数摘要。

## 决策

按计划 §3.4：

1. 每种消息只有一个幂等键：管理命令用 `command_id`，设备间调用用 `operation_id`。
2. 节点认证之外，接收方只在本机注册表把实例映射到该已认证节点时接受调用主体；Grant 存于接收方本机，不作为持有者令牌传递；查询、取消与订阅同样鉴权。
3. 首次执行副作用请求须携带接收方会话中最近下发的 `receiver_tick`，超出新鲜窗口返回 `STALE`，以同一 `operation_id` 携带新 tick 重试。
4. `operation_id` 的作用域为 `(已认证调用主体, 控制域 authority-owner, operation_id)`，绑定能力版本与按领域字段规范化的参数摘要；调用方在屏障前、接收方在持久接受时保存映射；ID 取自每主体单调序号，接收方回收记录时保留低水位，低于低水位且无记录的请求返回 `EXPIRED`。
5. 查询结果区分 `FOUND`、`EXPIRED_UNKNOWN` 与 `NOT_ACCEPTED`；只有接收方在同一提交中持久封禁该 ID 时，`NOT_ACCEPTED` 才是权威未执行结论。
6. `operation_id` 与 `(logical_call_id, binding_id)` 一一对应；换用绑定须先取得权威未执行结论并封禁旧 ID。

## 后果

- 节点冒充、长延迟、双方分别重启和去重记录回收后的重试都有确定行为，且不需要跨设备时钟同步。
- 接收方需保存每主体低水位与封禁记录；tick 随会话保活下发，不额外增加往返；离线跨节点委派暂不支持。

## 备选方案

- **持有者令牌（UCAN、Biscuit 一类可收窄的委派令牌）**：支持离线委派，但增加撤销与密钥管理复杂度；出现离线委派需求时再评估。
- **以绝对时间戳证明新鲜度**：依赖可信同步时钟，否决。
- **只设有限保留窗口而不保留低水位**：过期后旧请求可能被当作新动作执行，否决。

## 验证

`MA-038` 以 FakeTransport 覆盖节点冒充、实例被错误节点声称、首次到达长延迟、双方分别重启、去重记录回收后重试与查询后原消息迟到；E2 F9 覆盖管理命令幂等；M5 由 `MA-016` 在真实配对与认证下复核。
