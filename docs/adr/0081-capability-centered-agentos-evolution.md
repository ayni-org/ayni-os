# ADR-0081：通用能力接入与 AgentOS 架构演进

- **状态**：提议；用户已确认当前平台本机能力优先、远程控制可选，其余产品、兼容及具体实施次序以详细计划的待决项为准。
- **日期**：2026-10-29。
- **关联**：计划 §2、§3、§6、§8、§9；ADR-0008、0009、0010、0045、0046、0054、0080。

**后续决定**：AP-00/AP-01 的实际交付及存储决定见 ADR-0082；用户明确的通用 AgentOS 定位和基础先于平台实验的现行路线见 [ADR-0083](0083-general-foundation-before-platform-experiments.md)。下述原提议保留其讨论范围，未选择的接口和兼容选项不据此记为已批准。

## 背景

用户希望 Ayni 成为跨平台、跨设备的原生通用 AgentOS。硬件、软件和外部服务应通过公开能力描述与调用契约，供模型在 Tool Loop 中发现、理解和使用；驱动和底层设备操作由能力提供者实现。只定义注册函数，不能覆盖使用说明、发现、结果、取消、资源和恢复。

用户 2026-10-29 进一步明确：优先在当前平台调用该平台的设备与软件，类似直接执行命令；网络控制远程设备保留为可选扩展。因此，本机驱动/OS API/软件与受管命令适配是主要执行路径，本机纵切不依赖远程协议或中心网关；模型推理仍可使用外部 API。

现有 Core 已交付有界目录、授权、资源协调、三形态调用和可靠完成等机制；设备目录主要保存身份，模型工具描述主要使用 binding ID，业务请求仍以有限授权 fields 加 text 为主。完整自描述、大目录发现、通用业务 Schema 和跨平台后端尚需演进。证据、分期与待决事项集中在[通用能力架构与实施计划](../architecture/capability-centered-agentos-plan.md)。

## 提议

1. 保留现有八模块 Core、单 owner 与提交路径。Core 只持有执行与治理需要的有界权威事实；不新增平行的设备管理器、工具路由、授权目录或调用账本。
2. 硬件和软件共用能力定义、使用说明、Provider offer、Binding 与调用协议。Device/Component 为可选关联，纯软件能力无需伪造物理设备；资源身份和物理控制域仍明确。
3. 能力扩展持有规范语义和使用说明。模型 Provider 只消费受约束视图并做厂商编解码；首个 helper 在现有 submit 回调作用域内构造并复制，第二消费者出现后再提取公共辅助层。
4. 先补现有工具的语义说明，再按真实需求增加有界 typed 业务参数/结果、授权字段映射和受管发现。自然语言不成为限值，发现不授予权限，旧视图不替代派发前复核。
5. 复用 unary/action/subscription、Task、ActionRecord、可靠邮箱、执行许可与停止机制。媒体字节和设备句柄留在后端，长操作、取消、终态、物理停止和未知结果分别表达。
6. Host 提供系统基础，Provider/驱动实现能力，应用/策略组织工作；runtime 只选择、装配和管理生命周期。通用应用编排从 Native runtime 提取时保持既有行为。
7. 能力资源与实现特性迁往有效 Binding 契约仅为候选，需双实例证据、兼容决定和独立实现；本次不改变当前 ABI、storage schema 或已接受调用的匹配规则。
8. MCP、ROS 与 MHS 是独立适配路线。MHS 在可实施规范、访问、许可和夹具可得前仅参考公开设计，不声明兼容；不将本计划当作启动 M2、硬件或新测试专项的授权。
9. 本机能力优先方向由用户确认。本机与远程按实际执行目标区分，在能力视图和绑定中保持明确；本机不可用不隐式改投远端，不改变已接受调用。远程能力按需求后续交付，本机能力的注册、发现、调用与关闭先独立验证。
10. 原生枚举、MCP 列举与 ROS graph 只生成有界候选，由可信配置流程配对说明、确认身份/共享物理资源及健康报告者，在 CONFIGURING 复用已有注册。运行中新身份不热注册或暗换端点；配置重建保留旧 Call 的绑定和恢复要求。
11. 本机外部服务、直接远程第三方端点和 Ayni Kernel peer 各有进入门槛，第三方不必实现 Ayni peer；原 Bridge/peer 路线仍保留。协议取消可能没有最终响应，adapter 必须有限本地收口，保持真实 UNKNOWN、借用/ACK/join 及独立停止边界。
12. 现有代码的保留、迁移、条件替换和最小新增属主见[配套计划](../architecture/capability-discovery-and-adapters.md)。优先补扩展用法、协议/原生 backend 与共享应用边界；Mock、有效测试和平台骨架按职责保留；用户随后批准按 ADR-0082 删除已替代草案/bridge、统一存储格式，业务 parser 在实际替代后删除，不预建空插件框架。

## 后果

新增普通能力应集中修改扩展及部署配置，模型和 Core 能通过公开契约复用。代价是必须明确规范定义、授权投影、说明和运行事实的不同属主，并为类型、工具规模、说明字节、生命周期及兼容提供有界契约；公开接口不能替代这些约束。

资源绑定、业务 Schema、发现披露、媒体外发和后续实施次序仍按详细计划第 14 节决定。既有 optional 存储记录与原子批次兼容问题保持待决，不借本提议改写历史。

## 备选方案

- 将所有设备实现加入 Host 或通用 DeviceManager：混合系统基础与领域能力，变化范围扩大，不采纳。
- 只提供 register 加自由 JSON 调用：缺少类型、授权与执行语义，难以保证高内聚和兼容，不采纳。
- 每个模型 Provider 单独维护设备说明：重复设备知识且替换模型成本高，不采纳。
- 先引入动态插件、完整 Schema 解释器和通用发现总线：缺少当前必要性与资源证据，延后。
- 一次迁移所有现有调用、资源和持久格式：超出最小描述纵切，按独立可交付边界演进。

## 验证

本次交付为文档计划，契约、依赖、diff、仓库相对链接与原计划一致性检查通过，三位讨论代理复核职责与分期，发现的启动顺序、说明读取及投递借用表述已修正。检查和复核结果集中在 [#104](https://github.com/RobotSe7en/ayni/pull/104)。新的能力协议、平台实现及其验收结果由后续各工作包提供，不将本次讨论记作执行证据。

用户随后要求两位子智能体细化摄像头发现、MCP/MHS/ROS 和代码取舍，两方分别只读核查后交叉形成共识并补入同一 PR。补充仍为规划，不改变当前 ABI/schema、既定兼容语义或硬件支持状态。
