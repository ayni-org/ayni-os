# ADR-0002：提交与输出门控协议

- **状态**：已接受（设计基线，待实现与验证）
- **日期**：2026-10-18
- **关联**：计划 §2.4、§2.8、§4.3；`MA-010`；E2 F2、F8、F11、F12

## 背景

v1.3 §2.8 规定“异步写入中的变更处于暂存状态；有依赖的后续推进等待确认，独立任务可继续”，但没有定义依赖。两个 transition 共享设备总预算、Grant 或 Resource 时：若视为依赖，几乎所有推进都串行等待 Flash 提交；若不视为依赖，后者的准入建立在未持久状态之上，前者写失败时需级联撤销或维护多版本状态。v1.3 也没有定义写结果未知如何对账，以及写失败时 Host 仍有动作在途怎么办。

## 决策

按计划 §2.8 采用两层协议：

1. 持久层只证明连续持久前缀 `durable_seq`，恢复精确返回该前缀，不理解输出语义。
2. Kernel 只维护一份内存状态，按 `commit_seq` 顺序立即应用 transition；每个对外输出带 `requires_seq`，在 `durable_seq ≥ requires_seq` 后释放。具有副作用的 submit 另做最终复核，并保留 §4.3 中“复核与 submit 之间不处理其他普通意图”的顺序。
3. 写入 `FAILED/UNKNOWN` 时，先以相同 transition 有界重试；仍失败则进入受限栅栏（FENCED）：停止新输出、新准入与执行许可续租，在途动作按能力属性继续或取消，完成事件只进入易失缓冲；随后以新 `boot_epoch` 从持久前缀重载，存储仍不可写时进入只读诊断。
4. 不在内存中回滚部分 transition。

## 后果

- 只有一份状态，不需要依赖追踪，也没有单独的回滚路径；派发屏障成为输出门控的一个实例。
- 存储失败复用重启恢复路径，该路径已由 E2 故障矩阵覆盖；结合 ADR-0001，存储失败时执行器在剩余租期内停止。
- 查询须标注 `durable_seq`；受限栅栏期间服务中断，属于安全优先的取舍；ESP32 上写失败到重载完成的耗时须实测。

## 备选方案

- **每对象暂存版本加依赖追踪**：相当于在 ESP32 上实现带级联中止的多版本状态，实现与测试成本高，否决。
- **写失败时就地回滚内存**：后续决定可能已依赖未持久状态，回滚无法完整，否决。
- **所有推进都等待提交**：Flash 延迟下串行化全部工作，否决。

## 验证

`MA-010` 与 E2 F2、F8、F11、F12。另做属性测试：随机 transition 序列在任意点注入崩溃或写失败，断言每个已释放输出的 seq 不超过恢复后的 `durable_seq`，且恢复状态等于已提交前缀。
