# ADR-0032：可读性机械检查与复查交付证据

- **状态**：已接受；R1 本地验证与独立审查通过，PR/CI 记录见下文。后续整理尚未完成。
- **日期**：2026-10-23
- **关联**：`MA-006` R1～R4；[详细实施计划](../ma006-implementation.md)；[A–D 复查](../../reports/core/ma006-a-d-review.md)；计划 §9.1、§14.1；`AGENTS.md`；`docs/workflow.md`

## 背景

A–D 的复查发现职责、重复规则、隐式状态和注释问题。现有原则未形成逐项可核查的审查证据，历史验证原始记录又主要保存在仓库外。用户已要求将整改和 E/F 计划写入仓库并开始实施；本轮先交付 R1～R4，结束后保留 E 的开工停点。

## 决策

1. **先约束，再整理与修复。** R1 落实复查第 5、6 节的要求、检查器及历史基线；R2 按职责继续拆分行为不变的整理；A1 的行为修复单独交付 R3；R4 收尾状态文档和契约引用。单个部分的生产代码增删超过约 1,500 行时继续拆分。完整范围与三项 E/F 产品决定以详细实施计划为准。
2. **自动检查只负责机械规则。** 词法扫描 Core 具名函数的物理行数、同目录同名头源模块的注释比例、ID 辅助头外的指定移位/掩码模式，以及公开状态/原因码的相邻注释。规则来自复查，不通过脚本判断模块职责、抽象质量、注释含义或业务重复。宏生成函数、独立 lambda 等语法边界见 `docs/development.md`；语法不能可靠处理时报告错误，不伪造通过。
3. **可审查的增量基线。** `tools/readability_baseline.json` 以规则、路径和声明/表达式标识现存债务，不以行号匹配。新增或加重的违例使检查失败；问题消除后须删除基线项。非 ID 位运算仅用精确表达式、计数上限和原因作例外。CI 不自动生成基线，人工刷新也必须审查 diff。
4. **人工审查仍是完成条件。** 作者自查与独立审查逐项报告删掉的注释、Kernel 新字段、重复公式、裸数字，并给出位置或搜索范围。不能用检查器通过替代结论，也不能用无用注释满足比例。R1/R4 的文档和工具也独立审查；Core 逻辑仍按 workflow 由另一个会话出变异题，首次结果与补测结果分开记录。
5. **证据与状态分开。** 状态入口只写完成、下一步和待决定项；验证数字、配置、限制与可复现方法放在 ADR 和 PR。仓库外日志明确标记存放位置，不能声称读者可从仓库复核。已合并工作的条件句由 R4 清除。
6. **兼容边界。** R1 不修改 `core/`、`include/`、ABI、持久格式或产品行为，不需要迁移，也不执行 Core 变异。三项 E/F 决策已写入主计划 §14.1 和详细计划，尚未成为已实现能力。

## 后果

- 规则与基线进入 CI/CTest，旧问题仍可见；后续整理应逐项减少债务。
- 词法检查没有编译器的完整语义，语法扩展需要针对性的正反例和独立审查。通过只表示已识别的机械规则没有新增违例。
- 注释比例不能衡量注释质量，函数变短也不能证明职责清楚；人工审查承担这些判断。
- R1 增加开发工具的维护成本，不增加 Kernel 内存或运行时工作。

## 备选方案

- 只保留原则性要求：无法稳定发现本次已反复出现的机械问题，改为自动检查加逐项审查证据。
- 一次清掉所有债务再启用检查：会把检查器、重构与行为修复混在一起，采用显式基线分批收敛。
- 用完整 C++ AST 判断全部规则：需要编译配置和额外工具绑定，也仍无法判断设计质量；本次保留小范围词法检查，明确语法边界。
- 把脚本通过作为可读性完成证明：不能覆盖职责、命名与语义，拒绝。

## 验证

原始日志存放在仓库外 `../ayni-ma006-evidence/r1/`，仓库中的测试与 CI 提供可重新运行的检查。以下为本次实际运行结果，不复用 A–D 的验证数字。

- **环境与资源。** Native/x86-64，`ayni-m0-tools:latest`：GCC 13.3.0、Clang/clang-format 18.1.3、CMake 3.31.6、Ninja 1.11.1、Python 3.12.3。开始前宿主约 17 GiB 可用、swap 已用约 495 MiB、内存/CPU 压力均为 0；构建和 CTest 并行度均为 2，单个容器限制 2 CPU、3 GiB 内存、无额外 swap。五配置顺次执行，容器峰值 991,014,912 B，OOM 计数为 0；期间宿主内存压力仍为 0。复用已有构建目录以控制磁盘占用。
- **构建与运行。** GCC Debug、Release、ASan+UBSan、TSan、Clang Debug 均构建成功，各 CTest **894/894** 通过；模拟器 ABI 0.19，CONFIGURING→RUNNING→STOPPED，退出 0。GCC TSan 在宿主 `mmap_rnd_bits=32` 时启动失败，按 workflow 临时设为 28 后通过；随后恢复到 32 并核对，记录在 `tsan-host-setting.json`。
- **工具检查。** 最终 Python 工具测试 **83/83** 通过，其中可读性检查器 **34/34**；依赖、契约、clang-format 18、diff 检查通过。检查器复核修复后，在五个配置中单独重跑两项 readability CTest，均通过。验证编排曾在容器 Git ownership 检查处停下，保留该次记录；对明确挂载的 `/workspace` 使用单次命令的 `safe.directory` 后，完成剩余格式/diff 和工具版本检查，不修改全局 Git 配置。
- **基线。** 当前词法扫描列出 51 项历史问题：6 个长函数、15 项 ID 位运算表达式、7 个低注释比例模块、23 个缺相邻说明的公开码；另有 1 项经代码复核的非 ID 例外（commit marker 的低 32 位）。新增/加重、问题消除后残留基线、重复或无效基线均有失败测试；不把这 51 项写成已修复。
- **独立审查。** 独立只读会话 `r1_review` 发现四个可复现问题：默认模板参数/显式特化漏检、字符前缀误报、公开头文件 ID 模式漏检，以及未加括号的模板比较/移位表达式静默漏检。均先用新增测试复现，再修复；最终独立重跑 34/34 和仓库基线通过，四项问题关闭。最后一项选择明确报错并记录语法边界，未扩展为完整 C++ 解析器。

作者自查和独立审查分别核对了以下四项，结论一致：

| 项目 | 作者自查 | 独立审查 |
|---|---|---|
| 删除注释 | 检查完整 diff，`core/`、`include/` 无变更，无删除生产注释 | 独立检查相同范围，无删除生产注释 |
| Kernel 新字段 | `kernel_state.h` 及 `core/` diff 为空，无新增或迁移字段 | 无新增字段，无状态归属变化 |
| 重复公式 | Core 规则未变；机械规则统一在检查器，测试从输入/输出验证边界 | 未引入平行业务机制；词法问题按上表修复 |
| 裸数字 | Core/公开接口无新增数字；80/150/5 在检查器具名并对应复查 §6 | 阈值出处清楚，公开头文件 ID 检查缺口已关闭 |

R1 没有 Core 逻辑变更，不执行 Core 变异、不重测 caller arena 或覆盖率；未做 ESP32 本地构建、烧录或硬件验证。[PR #30](https://github.com/RobotSe7en/ayni/pull/30) 与其 [CI checks](https://github.com/RobotSe7en/ayni/pull/30/checks) 提供仓库外原始日志之外的可查证据；实际合并状态以 PR 为准。
