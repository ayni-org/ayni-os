# ADR-0009：IDL 与本地 API 编码

- **状态**：提议
- **决定时点**：M1 早期，基于 ESP32 实测
- **日期**：2026-10-18
- **关联**：计划 §3.1、§3.2、§3.4；`MA-005`、`MA-017`

## 背景

需要一份契约来源，生成 C 类型、线格式、存储映射与 conformance fixtures，避免手工维护多份表示导致漂移。本地 API 是否也先编码再提交，会影响 ABI 面大小、校验路径与 ESP32 资源占用；但统一校验并不要求本地调用必须先序列化。

## 已接受的约束

- 每类领域意图只有一个领域类型与一个语义校验器；本地类型化 API 与网络解码器构造同一类型并共用校验器。
- 幂等参数摘要按契约列出的领域字段规范化计算，不对任何序列化字节取哈希（Protobuf 官方说明其序列化不是规范化表示）。
- ABI、线协议与存储三类版本独立演进（计划 §3.1）。

## 候选方案

| 方案 | 优点 | 代价 |
|---|---|---|
| Protobuf + nanopb | 演进规则成熟，有标准 JSON 映射，有 MCU 实现 | 序列化非规范化；生成代码体积须实测 |
| CBOR + CDDL | 适合 MCU，标准化 | 代码生成与工具链较弱 |
| 自定义 Schema 与生成器 | 完全可控 | 维护成本高 |

本地 API 的两种形态：

- **(a) 类型化结构直调**：本地类型化结构直接调用语义校验器。
- **(b) 编码消息提交**：本地调用也编码后经单一入口提交，ABI 面更小。

## 决定依据

以代表性消息测量：ESP32 固件体积增量、峰值 RAM、最大消息编解码延迟、生成代码的可审查性，以及依赖许可证。测量结果写入 `reports/core/` 后再决定。

## 验证

选定后，contract fixtures 做双向往返测试；本地与网络两条路径对同一组正例和反例给出相同的校验结论。
