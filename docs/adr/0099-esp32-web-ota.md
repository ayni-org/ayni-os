# ADR-0099：独立 ESP32 Wi-Fi 实验的 Web OTA

- 日期：2026-11-11
- 状态：已接受；正常部署验证见独立实验记录
- 范围：`experiments/esp32_wifi_chat`，不改变 Core、ABI0.54 或 schema9

## 背景

用户要求脱离 USB、使用充电宝时仍能更新。现有固件只有 factory 槽；旧3 MiB音频区已停用。用户明确选择将 OTA 与内部栈内存修复一起做完，再经 USB 安装；允许先完整备份并改用旧音频区，保留 Wi-Fi、遥控器配对及8 MiB Ayni数据区。（产品语义，用户选定推荐项）

## 决策

1. 初次 USB 引导由独立 `ota_install.py` 负责；严格匹配板卡和新旧布局，完整备份 bootloader、分区表、空白元数据区、旧音频及原应用，再写新的 bootloader、表、OTA元数据及新应用。原应用地址0x410000保持为已确认的回退槽；不写 NVS 或 Ayni 卷。USB 引导不声称具有断电原子性。
2. `otadata` 位于原空白0x9000、大小0x2000；`ota_0` 为0x100000/0x300000；`ota_1` 为0x410000/0x3f0000。`demo_cfg`、`nvs`、`ayni` 的地址、大小、类型和标志保持。后续应用上限取两槽较小值3 MiB。既有 `device.py deploy` 拒绝 OTA 候选，避免旧固定地址流程覆盖回退槽。
3. `/update` 与 GET/POST `/api/firmware` 沿用用户已选定的局域网 HTTP、无验证码方式，验证数字 Host/同源，不自动重传。只上传本实验的完整应用 bin，不接收 bootloader/分区表包。此入口不是公网或不可信 LAN 的更新认证方案；未启用固件签名或 eFuse 防降级。
4. Runtime 负责用户输入、设备停止和关闭顺序；HTTP 任务负责有界收包、SDK OTA 句柄与闪存写入；`UpdatePlan` 只拥有进度、关闭及应答屏障。首部确认项目、长度后请求 UI 维护，忙碌/录音时拒绝；沿用原维护停止及 Core/Host 正常关闭，等所有借用 I/O 退出并收到 STOPPED 后才写备用槽。关闭未确认时不强制重启。
5. SDK 完整镜像校验通过后才选择新槽；HTTP 应答尝试完成并留1秒宽限后重启。写入失败但已关闭会话时通过重启恢复运行，界面明确结果未确认；不伪造成功，也不自动再次上传。
6. 启用 ESP-IDF6.0.3 软件回退，未启用 eFuse anti-rollback。新镜像待确认期间禁止新对话和设备操作；配置、触摸、Web、Wi-Fi及 Core 会话连续就绪5秒后确认；60秒不能就绪时请求 SDK 回退。只声明软件已实现；未执行断电、镜像破坏、回退或其他新的故障/恢复专项。
7. 用户2026-11-14明确取消刷写前断开电机驱动电源的人工前置要求。正常OTA不查询驱动供电，也不再等待断电确认；第4项的软件停止、排空及真实关闭屏障保持。硬件复位失能／独立停止链未验证的事实和本次正常OTA的证据边界见ADR-0101第7项。（操作条件，用户明确变更）

## 兼容与替代方案

保留单 factory 槽无法支持安全地写备用镜像；移动 Ayni 卷会引入不必要的数据迁移，因此复用停用音频区。新旧数据格式不变，普通 OTA 不迁移存储；未来格式变化仍须独立兼容决策，不能从同项目名称推定数据兼容。必要时 USB 可恢复本机完整旧布局备份；Web OTA 不负责回刷 bootloader 或分区表。
