# ADR-0007：通知呈现复用能力调用与 Task 状态维度

- **状态**：已接受（设计基线，待实现与验证）
- **日期**：2026-10-18
- **关联**：计划 §2.4、§2.7、§5.4；`MA-004`、`MA-011`、`MA-019`；E1 步骤 11、E4 步骤 7

## 背景

- v1.3 §5.4 为通知定义了独立的状态机、delivery ID、重复回执去重和未知结果对账规则，这些规则与 ActionRecord 一一对应；计划本身也已把“通知”列为能力的副作用类别。通知位于应用层，却要与 Task 完成同批提交，而应用层不能直接修改 Core 状态，归属自相矛盾。
- Task 状态枚举混合了三个维度：生命周期、持久化状态（`ACCEPTING`）和由待决调用派生的等待原因（`WAITING_*`）。派生值与原始数据形成两个真相来源，单一枚举也无法同时表达多个待决调用。

## 决策

1. 每个渠道的呈现是声明“通知”副作用类别的 `notify.present` 能力，经 ActionRecord、`operation_id`、派发屏障与能力的去重/查询属性处理。提醒 GoalType 的完成条件是主呈现调用以成功证据完成；用户可见状态是计划 §5.4 表中对调用事实的投影；呈现能力声明独立截止时间。Kernel 不设通知专用状态机。
2. Task 只保留生命周期枚举；`blocked_on` 由待决调用派生；是否已持久接受由 `durable_seq` 表达（ADR-0002）。
3. 已确定的产品语义保持不变：普通提醒按选定方式成功呈现才完成，无需用户确认；失败或未知保持待处理；仅入列不算完成。

## 后果

- 少一套状态机、去重表和对账路径；E2 故障矩阵自动覆盖通知呈现；多个待决调用可以同时表达。
- 每次呈现尝试产生 ActionRecord 写入（原设计同样需要持久记录）；网页回执需要允许长时间 `IN_PROGRESS` 的 `action` 调用。

## 备选方案

- **保留独立的通知状态机**：重复机制且归属矛盾，否决。
- **把通知状态作为 Kernel 领域对象**：把业务概念放入 Kernel，违反“业务类型由应用注册”，否决。

## 验证

E1 步骤 11 与 E4 步骤 7 使用同一套 E2 夹具运行；状态转换表测试；评审时检查是否有持久字段可由其他持久字段推导。
