# ADR-0005：ESP32 分层停止链

- **状态**：已接受（设计基线，待板级实测）
- **日期**：2026-10-18
- **关联**：计划 §4.1、§7.1、§7.3、§2.10；`MA-001`、`MA-026`；E2 F14

## 背景

“最高优先级任务 + 默认关闭 GPIO”只能表达启动禁用，不能证明运行中任务失效后仍能及时失能。ESP-IDF 文档说明：默认配置下，SPI Flash 写入或擦除期间缓存关闭，其他任务挂起、另一核忙等，只有 IRAM-safe 中断执行，PSRAM 也不可访问；Flash auto-suspend 是可选功能，依赖 Flash 芯片支持，官方说明它不适合严格实时及 Wi-Fi 等频繁中断场景。因此任务优先级本身不能支撑毫秒级停止承诺。

## 决策

按计划 §4.1 的四层停止链实施：

1. **L0 硬件切断**：急停直接切断驱动器使能，或接入 MCPWM GPIO fault 并采用需软件恢复的 OST 制动；使能脚外部下拉。
2. **L1 硬件超时**：外部看门电路要求使能信号持续翻转，停止翻转超过 `T_hw` 即失能。
3. **L2 IRAM 监督**：IRAM-safe 定时中断只在许可有效且控制任务心跳在 `T_hb` 内时翻转 L1 信号。
4. **L3 控制任务**：在包络内减速停止。

journal 扇区擦除在无活动执行器会话时预先完成，会话期间只做页编程，并要求 `T_hb` 大于实测最长页编程时间。最坏停止时间按 `T_hb + T_hw + 驱动器关断 + 机械停止` 分项实测。v0.1 只声明“在已测故障列表下的实测停止上限”。L0/L1 进入 M0 候选 BOM；是否增加安全 MCU 在 M3 实测后决定。

## 后果

- 停止上限不再依赖任务调度；每层的依赖与覆盖的失效可审计，硬件成本低。
- 增加少量元件与 GPIO 占用；journal 擦写调度受运动状态约束；`T_hb` 需要在误停与停止上限之间折中。
- 不声明独立安全功能或任何安全标准符合。

## 备选方案

- **仅依赖软件任务优先级**：Flash 操作期间失效，否决。
- **启用 Flash auto-suspend**：依赖芯片支持，且官方不建议用于严格实时场景；最多作为补充手段。
- **立即增加安全 MCU**：成本与集成复杂度较高，目前缺少证据，推迟到 M3 实测后决定。

## 验证

`MA-001` 给出候选电路与价格；`MA-026` 用逻辑分析仪记录使能脚，并以编码器/IMU 或高速视频记录实际停止。故障矩阵至少包括运动中 Flash 擦写、控制任务死锁、Kernel 任务死锁、panic/复位、欠压与 Wi-Fi 高负载，并在每种状态下触发急停。MCPWM fault 的强制输出是否完全不依赖 CPU 与缓存同样以实测为准。
