# ESP32 USB 屏幕与扬声器能力独立实验

本工程通过 Ayni 公开源码 SDK 接入，基础为 main `d58613c`，C ABI 0.53 / Core schema 8。Core、公开 C ABI、存储格式、原有策略及 runtime 保持原样；用户 2026-11-01 另行授权修复共用 HostStorage 与 ESP 文件适配的日志重开性能，保留设备数据。实验代码、构建和恢复资料留在本目录。

用户 2026-10-31 选择：USB、本地 Mac 窗口、DeepSeek `deepseek-flash`、最多 4 KiB 中文回复；屏幕必须注册为能力并由模型调用。真实模型密钥在本地窗口填写，不进入设备、源码、命令行参数或日志。

随后加入 MAX98357A 提示音及中文朗读，用户指定默认软件音量 80%。扬声器同样由模型发现、查看和调用；最终回复不会自动播放。

## 调用链

Mac 输入 → ESP32 上 Ayni Goal/Task → 模型 Provider → USB → Mac HTTPS → 模型提议工具 → Ayni 模型结果账本 → 独立策略发现/查看/请求 `screen.show_text` → Core 授权/参数/资源/派发屏障 → 屏幕 Provider → Mac 字体排版 → USB 位图 → ESP32 LCD DMA → Provider 完成 → Core 持久结果 → 后续模型确认。

最终 assistant 文字只出现在 Mac 窗口，不自动更新屏幕。只有真实屏幕调用建立的文档 ID 能提交位图；屏幕结果在设备收到 LCD DMA 完成后才成功。Mac 是屏幕 Provider 的字体后端，使用系统字体支持中文和标点；无需在 MCU 分发字体。首次显示成功后，可在 Mac 翻阅该已授权文档的其他页。导航不生成新的模型请求。

独立策略仅实现本实验的有界文字及展示能力组合：四个标准原生函数中 list/inspect/call 有正常路径，shell 明确不可用；每次模型响应至多一个工具提议。策略保护上限为 12 轮，Core 初始模型软限制为 8 轮，达到限制会保持任务而非绕过约束。没有把此策略声明为通用 ToolLoop 的替代品。业务参数及默认值通过公开的 `ayni_arguments_normalize` 处理；授权、结果账本、存储及 Core 调度均使用现有公开接口。

本版没有复用内建ToolLoop/Conversation编排：当时为独立4 KiB文字策略选择了自定义策略。但内建`turn_text_max=384`约束的是会话输入及最终文字，长屏幕正文可以放在工具参数中，最终仅返回短确认；因此屏幕正文4 KiB本身不要求替换内建ToolLoop。当前策略是实验取舍，存在重复编排，不覆盖内建上下文压缩、私有记忆、受管长任务等完整能力，不作为这些机制的验收证据。本次按用户要求提交当前实现，未额外开展ToolLoop迁移。

## 扬声器

MAX98357A：VIN→3V3、GND→GND、BCLK→GPIO4、LRC/WS→GPIO5、DIN→GPIO6。独立 `speaker.cpp` Provider 持有 I²S 和 PCM，注册两个能力，共用独占的 `speaker.slot` 资源：

| Capability / Binding | 参数 | 默认值与限制 |
|---|---|---|
| `speaker.tone` / `speaker.play_tone` | `frequency_hz`、`duration_ms`、可选 `volume_percent` | 100..4000 Hz、50..3000 ms，音量 1..100，默认 80 |
| `speaker.speech` / `speaker.speak_text` | `text`、可选 `volume_percent` | 1..1024 UTF-8 字节、合成音频最多 30 秒，音量 1..100，默认 80 |

中文朗读：模型提议 → Core 校验和派发 → Mac `/usr/bin/say` 使用已安装的 Tingting 中文语音合成到私有临时文件 → 严格读取 CAF 中的 16 kHz 单声道有符号 16 位 PCM → USB 顺序分块及 offset 回执 → ESP32 完整接收后播放。无云端语音服务，Mac 本身不发声；临时合成文件在合成结束后删除。超过文本或时长限制明确失败，不截断。

ESP32 沿用旧固件验证过的 48 kHz、16 位、双声道 I²S 格式，把每个 16 kHz 单声道采样重复三次并复制到左右声道，按音量百分比缩放振幅。这里的 80% 是软件采样幅度，不代表声压或功放增益。固定 PCM 缓冲区最多 960,000 字节，位于 PSRAM；音频 worker 的栈和 DMA 输出缓冲在内部 RAM，Core owner 不等待合成、串口或播放。

仅在实际 PCM 排空 I²S 并停止通道后返回 `played:true`；回执包含采样数、16 kHz 源采样率和实际音量。软件回执不能证明人听到了声音。两个调用都声明非幂等，取消/失败后的部分输出按未知处理，不自动重放。USB 协议升级为 v2，需同时更新固件和 Mac 桥接并重启窗口。

## 运行

1. 根据主机实际资源设置正数并行度。此 Mac 检查到 16 GiB RAM、10 CPU、无 swap 使用、无其他构建，选择构建/测试并行度 2，给桌面留余量。
2. `bash build.sh`：激活原任务已验证的 ESP-IDF 6.0.3；LittleFS 1.23.1 锁版；构建固件和原生 Mac 窗口。旧 SDK 的精确 XMC Flash ID 兼容补丁保留，Ayni Core 没有补丁。
3. 完成下面的设备预检，再执行显式部署。禁止使用生成的通用 `idf.py flash`，它会加入 bootloader 写入。
4. 运行 `./launch.command`，填写 API Key，连接后输入文本。默认 API 根地址 `https://api.deepseek.com`，模型 `deepseek-flash`，Chat Completions 非流式、关闭思考模式。模型配置在一个连接期间冻结；更改服务或模型需关闭窗口并重启设备。窗口关闭会请求正常停机；下次打开前先按开发板 RST，让设备重新等待配置。

输入和屏幕正文分别最多 4096 UTF-8 字节。累计发送给模型的上下文最多 16 KiB；达到上限时明确拒绝，使用“清空上下文”开始后续新上下文。该按钮只清空电脑内存，不宣称删除设备持久日志。API 和模型公开配置的 route ID 纳入 Provider/目的地身份；密钥不参与指纹。

HTTPS 保留证书验证，不跟随重定向，不读取环境代理，不自动重试。网络中断、取消或不完整响应不能证明远端未计费，结果按未知处理。超过正文上限或 token 截断明确失败，不静默截断。HTTP 状态可显示，原始 vendor 错误正文不输出。

官方模型接口依据：[DeepSeek 官方快速开始](https://api-docs.deepseek.com/quick_start/agent_integrations/)。实际联网结果单独记录，不能由离线夹具推定。

## 设备与旧固件恢复

只接受已验证 USB 身份：VID 1a86 / PID 55d3 / serial 5D01368694，端口 `/dev/cu.usbmodem5D013686941`。板型要求 16 MiB Flash / 8 MiB PSRAM。LCD 沿用 SCK12、SDI11、CS10、DC9、RESET8、RGB+INVON。没有启用旧录音、星图、Wi-Fi 或触摸服务。

使用原 IDF Python 执行 `device.py preflight`：保存旧 bootloader、分区表和整个 2 MiB 应用，确认当前应用与提供的旧固件一致，检查 `0x800000..0x1000000` 全部为 FF。它会重启板子，但不修改 Flash。不会读取 `demo_cfg` 凭据区。

`device.py deploy` 只写分区表 sector `0x8000` 和应用 `0x410000`；保留原应用地址/容量，以及 audio 和 demo_cfg 分区。只在已确认空白的高 8 MiB 新增 Ayni LittleFS。Host 显式允许首次初始化完全空白卷，未知非空白介质仍拒绝并保留。

`device.py restore` 恢复保存的原分区表及原 2 MiB 应用，不写 bootloader、eFuse、demo_cfg、audio 或 Ayni 数据卷。恢复脚本不会自动运行。恢复资料位于被忽略的 `artifacts/recovery/`，不要清理该目录。

## 验证边界

编译、Mac 排版/语音合成、桥接单测、ESP 实际运行、真实联网和用户感官确认分别记录。普通文本及屏幕/扬声器能力检查使用正常路径，不增加掉电、变异、耐久或其他故障专项。复现桥接测试：在 `desktop/` 执行 `python -m unittest -v test_bridge test_audio`。板上正常能力检查运行 `offline_check.py --speaker`，会实际播放 300 ms 提示音及一句中文，两个调用均省略音量参数，以检查默认 80%；不调用真实模型。

### 屏幕首版历史结果（2026-10-31）

- ESP-IDF 6.0.3（保留原 XMC 精确 ID 补丁）、Xtensa GCC 15.2.0、C++17 完整编译/链接通过；应用 691,056 字节，位于原 2 MiB 应用分区内。Mac arm64 使用 Apple Swift 6.4 编译并实际打开原生窗口，中文排版预览通过。
- 桥接单测 8/8 通过，覆盖分块 UTF-8/CRC/容量、原始数字 lexeme、重复字段拒绝、晚到结果，以及“最终答复不自动显示、屏幕 Provider 请求才排版”的边界。契约检查、现有 tracked 文件 diff/空白检查及新增源文件空白检查通过。没有本地重跑 Ayni 全套 CI 或覆盖率。
- 实际板上正常夹具通过：发现 → 查看 → 调用 `screen.show_text` → LCD DMA → Core 持久结果 → 模型确认 → 正常停机并 join。2,828 UTF-8 字节正文分成 12 页，第一页、最后一页及返回第一页均收到设备成功回执。不是联网模型结果。
- 同一正常长文本运行的 owner 栈余量 72,592/98,304 B（73.84%），存储 worker 14,136/24,576 B（57.52%）；内部 RAM 最小空闲 241,748 B，PSRAM 最大连续块 4,980,736 B。实际 Kernel arena 查询 2,266,944 B；它不包含 Host、串口/屏幕、应用、任务栈或其他堆。两项受检栈均超过 25% 余量；未测独立 I/O 任务栈水位。
- 用户在本地窗口提供密钥后，真实 `deepseek-flash` 两轮对话完成；窗口显示屏幕能力派发/完成及最终模型确认，第二轮文档为 2 页，用户实际翻页并反馈屏幕正常。密钥和现场完整对话未写入仓库或导出日志。
- 首轮实验装配问题已修正：模型 Binding 缺少匹配的外发目的地、目录调用未提供零 cursor；Ayni 库无变更。长 Flash 只读预检发生串口损坏，改用 512 KiB 分段有限重读后确认高 8 MiB 全 FF；没有把读取失败当成通过。

正常夹具事件和恢复二进制保存在本机被忽略的 `artifacts/`，属于未提交、未上传 CI 的现场证据。真实模型及用户目视的证据来自本次会话与实际窗口；不是公开发布、跨平台全验收、断电或耐久证明。旧固件恢复入口和完整原始应用/表已保留，本轮没有为验证恢复而再次刷回旧固件。

## 设计自查

- 模块：模型、屏幕、扬声器分别注册 Provider；Core 不依赖实验、Mac UI、串口、LCD 或 I²S。平台 I/O 在外部任务，owner 不等待网络、屏幕或播放。
- 删注释：Host原有持久化说明保留，旧固件零修改。移除的实验初稿自动显示逻辑已由屏幕工具调用取代。
- Kernel 字段：没有增加或复制 Kernel 私有字段。实验只保存公开对象 ID、命令回执及 Provider 借用。
- 重复机制：消息投影、参数树校验及默认值、业务 Schema 编码和 Core 账本复用公开实现；目录和能力编排仅限这个独立部署。保留此前的 `screen.N` 检查点键，避免只因命名改变已有步骤身份。
- 生命周期：受理的模型/显示调用保留 completion 直到终态 post；晚到的不同 Call ID 不替换当前结果；失败不冒充未发生。窗口关闭请求正常停机。
- 音频所有权：接收中的 PCM 由 I/O 任务在短临界区内写入；完整提交后成为 worker 只读借用，晚到数据不能修改它。结果通过原子完成标志回到 owner；Core 停止后 join 音频 worker，再释放其内部 RAM。
- 重要限制：Mac 是受信任本地配置/模型及字体边界；本实验不是恶意电脑隔离。显示回执证明 DMA 完成，不替代屏幕目视验收。整部分跨平台/耐久验收不在本实验内。
