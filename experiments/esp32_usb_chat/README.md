# ESP32 USB 屏幕、扬声器与电机能力独立实验

本工程通过 Ayni 公开源码 SDK 接入，2026-11-03 按用户要求改到 main `44f65d0`：C ABI 0.54 / Core schema 9，复用内建 ToolLoop 与 Conversation 记录。Core 与公开 C ABI 没有为本实验改动；`strategies/builtin/conversation.cpp` 修了一处只在 32 位目标暴露的 `uint64_t`→`size_t` 编译错误（行为不变）。用户 2026-11-01 另行授权修复共用 HostStorage 与 ESP 文件适配的日志重开性能。实验代码、构建和恢复资料留在本目录。

**从旧固件升级前必须擦除 `ayni` 数据卷。** schema 9 不迁移旧版（schema 8）日志，旧卷只能只读打开，设备会报告 “Core storage restricted or fenced” 并停在未就绪。驱动断电后执行 `device.py erase-volume`，它只擦 `0x800000..0x1000000`，不碰应用、分区表、audio、demo_cfg 或 bootloader；随后 Host 把全空卷初始化为新卷。旧日志与旧会话记录随之删除，这一步需要用户自己决定后执行。固件和 Mac 桥接必须同时更新（USB 帧 v4）。

用户 2026-10-31 选择：USB、本地 Mac 窗口、DeepSeek `deepseek-flash`、最多 4 KiB 中文回复；屏幕必须注册为能力并由模型调用。真实模型密钥在本地窗口填写，不进入设备、源码、命令行参数或日志。

随后加入 MAX98357A 提示音及中文朗读，用户指定默认软件音量 80%。扬声器同样由模型发现、查看和调用；最终回复不会自动播放。

当前增加人工台架的真实 `motor.run` / `motor.stop` 能力，候选构建位于 `build/motor-firmware/`。用户明确选择每次模型提议由 Mac 人工批准，PWM 可调、硬上限90%，单次最多5秒；这不是无人运动配置或独立硬件停止链验收。原人工验线入口 `motor_probe/` 继续保留；旧固件恢复资料完整保留。


## 调用链

Mac 输入 → ESP32 会话记录存入输入正文 → Ayni Goal/Task → 内建 ToolLoop 组请求（系统说明、摘要、此前各轮、本轮输入）→ 模型 Provider 从正文存储读出请求 → USB → Mac 加模型名与密钥后 HTTPS → 模型提议工具 → Ayni 模型结果账本 → ToolLoop 发现/查看/请求 `screen.show_text` → Core 授权/参数/资源/派发屏障 → 屏幕 Provider → Mac 字体排版 → USB 位图 → ESP32 LCD DMA → Provider 完成 → Core 持久结果 → 后续模型确认 → Task 完成 → 新会话记录持久后才把回复发给 Mac。

最终 assistant 文字只出现在 Mac 窗口，不自动更新屏幕。只有真实屏幕调用建立的文档 ID 能提交位图；屏幕结果在设备收到 LCD DMA 完成后才成功。Mac 是屏幕 Provider 的字体后端，使用系统字体支持中文和标点；无需在 MCU 分发字体。首次显示成功后，可在 Mac 翻阅该已授权文档的其他页。导航不生成新的模型请求。

编排由内建 ToolLoop 完成，实验不再有自写策略。ToolLoop 使用四个标准原生函数（list/inspect/call，shell 不可用），每次模型响应 1..8 个工具提议整组保留原始 ID、按顺序执行，完整工具组及结果齐备后才请求下一轮。七项运行设置集中在 `firmware/main/harness.h`：上下文窗口 8192 估算 token、输出 1800、超出后压缩到 4096、单个工具结果 1024、每轮最多 12 次模型调用（顺序扬声器检查本身需要 8 次）、请求超时 90 秒、模型并发 1。达到调用上限时 Core 暂停任务，不绕过约束。系统说明原在 Mac 桥接，现随 ToolLoop 配置在设备上；Mac 不再拼接历史，只转发设备给出的请求。实验只包一层准入：会话 ready 之前和关机开始之后，已恢复的旧 Task 不做决策。

会话记录归设备：`history.cpp` 把一条记录写在 Host 的值文件里，记录引用的正文（各轮、摘要、本轮输入）放在共用正文存储（`FileBodies`）。只有完成的回合才改记录；失败、取消或复位中断的回合不进入记录，下一轮或下次开机都从上一份已存记录继续，不重放未完成请求。回复在命名它的记录持久后才发给 Mac。新记录保存后，旧记录不再引用的正文文件随即删除，包括开机时读入的旧正文。“清空上下文”让设备删除全部轮次与摘要，同样持久后才回报 “context cleared on device”。

记录本身跨断电保留，但能带进下一次开机的只有此前的用户输入：内建 ToolLoop 把能力目录的披露绑定到开机代次，新开机后的第一轮会清掉旧回复、工具历史和摘要，旧输入只作为“历史用户输入、不得执行”的数据保留。打开串口会复位开发板，所以每次重新连接窗口，模型都看不到上一段会话的回复。复位打断的回合，其输入正文（每条最多 4 KiB）不在记录里，会留在数据卷上，直到擦卷。

owner 循环不再每毫秒轮询：每次 `ayni_step` 后，按步进报告 `more_ready` 立即再走，否则睡到下一个 Core 截止时间或被唤醒（最长 100 ms，供设备自查的超时使用）。Core 自己的完成、USB 收包、扬声器 worker 和电机控制任务都会唤醒 owner；连续忙碌时每 20 ms 让出一个 tick 给 IDLE 与看门狗。

## 扬声器

MAX98357A：VIN→3V3、GND→GND、BCLK→GPIO4、LRC/WS→GPIO5、DIN→GPIO6。独立 `speaker.cpp` Provider 持有 I²S 和 PCM，注册两个能力，共用独占的 `speaker.slot` 资源：

| Capability / Binding | 参数 | 默认值与限制 |
|---|---|---|
| `speaker.tone` / `speaker.play_tone` | `frequency_hz`、`duration_ms`、可选 `volume_percent` | 100..4000 Hz、50..3000 ms，音量 1..100，默认 80 |
| `speaker.speech` / `speaker.speak_text` | `text`、可选 `volume_percent` | 1..1024 UTF-8 字节、合成音频最多 30 秒，音量 1..100，默认 80 |

中文朗读：模型提议 → Core 校验和派发 → Mac `/usr/bin/say` 使用已安装的 Tingting 中文语音合成到私有临时文件 → 严格读取 CAF 中的 16 kHz 单声道有符号 16 位 PCM → USB 顺序分块及 offset 回执 → ESP32 完整接收后播放。无云端语音服务，Mac 本身不发声；临时合成文件在合成结束后删除。超过文本或时长限制明确失败，不截断。

ESP32 沿用旧固件验证过的 48 kHz、16 位、双声道 I²S 格式，把每个 16 kHz 单声道采样重复三次并复制到左右声道，按音量百分比缩放振幅。这里的 80% 是软件采样幅度，不代表声压或功放增益。固定 PCM 缓冲区最多 960,000 字节，位于 PSRAM；音频 worker 的栈和 DMA 输出缓冲在内部 RAM，Core owner 不等待合成、串口或播放。

`MODEL_TOOLS` 保留 USB v2 的单提议格式，并新增 batch-v1 包装：8 字节 `<HHHH>` 为 `(0, 0, count, 1)`，随后每个成员由 `<I>` 字节长度及原单提议包组成。原单包的 ID 长度必须非零，因此两种格式无歧义；整组最多 8192 字节、每成员最多 32 个参数节点，超限或重复 ID 整组拒绝。设备复用 `ayni_tool_calls_measure` 校验完整组和持久编码容量。这段工具负载编码保持不变；当前帧协议为 v4（v3 加 32 号 `forget`，USER 改为纯 UTF-8 输入），旧 Mac/固件必须成对使用，不会跨版本接收。

仅在实际 PCM 排空 I²S 并停止通道后返回 `played:true`；回执包含采样数、16 kHz 源采样率和实际音量。软件回执不能证明人听到了声音。两个调用都声明非幂等，取消/失败后的部分输出按未知处理，不自动重放。当前 USB 帧协议为 v4，需同时更新固件和 Mac 桥接并重启窗口。

## 运行

1. 根据主机实际资源设置正数并行度。此 Mac 检查到 16 GiB RAM、10 CPU、无 swap 使用、无其他构建，选择构建/测试并行度 2，给桌面留余量。
2. `bash build.sh`（当前构建目录 `build/motor-firmware/`）：激活原任务已验证的 ESP-IDF 6.0.3；LittleFS 1.23.1 锁版；构建固件和原生 Mac 窗口。旧 SDK 的精确 XMC Flash ID 兼容补丁保留，Ayni Core 没有补丁。
3. 完成下面的设备预检，再执行显式 `device.py deploy --variant motor` 部署。禁止使用生成的通用 `idf.py flash`，它会加入 bootloader 写入。
4. 运行 `./launch.command`，先确认驱动10V电源关闭、两轮静止，再填写 API Key并连接。串口实测开关会复位ESP32，因此带电期间保持同一连接；窗口 ready 后才由在场用户打开驱动电源。默认 API 根地址 `https://api.deepseek.com`，模型 `deepseek-flash`，Chat Completions 非流式、关闭思考模式。模型配置在一个连接期间冻结；更改服务或模型需关闭窗口并重启设备。用户 2026-11-01 选择每次重开取消旧的未完成实验任务、保留日志和已完成的会话记录；公开取消命令及任务终态持久确认后才发送 ready。策略在此之前不提出新调用。窗口关闭同样先取消实验任务，再请求 Kernel/Host 正常停机；下次打开前先按开发板 RST，让设备重新等待配置。

输入和屏幕正文分别最多 4096 UTF-8 字节。上下文超过窗口时由 ToolLoop 用一次纯文字模型调用压缩较早的轮次，不再要求手动清空；“清空上下文”删除设备上的会话记录，不删除 Core 日志。设备请求最大 32 KiB JSON，Mac 只接受 1..8192 的 `max_tokens`，仅在请求带工具时加 `parallel_tool_calls:false`。API 和模型公开配置的 route ID 纳入 Provider/目的地身份；密钥不参与指纹。

LCD 在显示关闭时用原有 16 行 DMA 缓冲逐条清成黑色，全部完成后才点亮；等待模型配置和首条屏幕能力调用时保持黑屏，避免上电显存杂色。启动清屏属于驱动初始化，不伪造屏幕工具调用或模型回复。

## 电机人工台架能力

芯片丝印为用户确认的 TA6586；D0→GPIO38、D1→GPIO39、D2→GPIO40、D3→GPIO41，共地，驱动板3V3辅助输出留空。驱动 VIN 为独立10V，两电机额定12V；车轮架空，有独立断电开关。[TA6586 数据表](https://components101.com/sites/default/files/component_datasheet/ta6586-datasheet.pdf) 中两输入低为高阻滑行、两输入高为制动。正百分比选择D0/D2，负百分比选择D1/D3；另一输入保持低，以1kHz PWM驱动/滑行。正负不是已标定的车辆前后方向。

| Binding / Capability | 输入 | 执行意义 |
|---|---|---|
| `motor.status` | `{}` | 配置接线、限值、台架使能；电源/机械状态未测量 |
| `motor.plan` | 两个百分比 -90..90，`duration_ms` 1..5000 | 纯计算，`executed:false`，不会转动 |
| `motor.run` | `motor1_percent`、`motor2_percent`：-90..90整数；`duration_ms`：50..5000且为5的倍数 | 每次人工批准后输出；0使该路滑行，两路均0拒绝（请用stop） |
| `motor.stop` | `{}` | 提交锁定停止请求；工具返回不冒充停止确认 |

`motor.run` 是非幂等 PHYSICAL action，复用 Core Grant、规范参数投影、独占 actuator、Scene、ExecutionBinding及现有独立 `Ayni::PermitGate`。能力说明、规范参数和许可约束来自同一字段定义。启动内授权最长24小时，到期不自动续权；须驱动断电后关闭并重新连接。旧未完成任务仍由原会话清理规则取消，不恢复重放物理动作。

执行端在受理时复制 Core 的真实 call/operation/attempt/permit身份并启动门控，但没有第一份采样、没有PWM。Mac逐次展示两个占空比和时长，只有准确身份及一次性nonce匹配、30秒内人工批准，执行端才能产生采样并启动RMT。拒绝或超时不输出。门控procedure总预算60秒，含人工等待；实际波形最多5秒，不续租。RMT使用有限硬件循环、低电平结束；四个PCNT覆盖准备、输出及释放，要求选中脚边沿数等于duration_ms、其余脚为零。PCNT不是编码器反馈，不能证明轮子达到目标。

每次输出结束先停RMT、解除GPIO矩阵并本机读回四脚低，才向PermitGate确认**控制器输出已停止**；target始终UNVERIFIED。正常结束直接返回结果，不再额外要求一次“人眼确认后才结束调用”。结果的operator_stopped为null/source为not-requested，不伪造人眼或传感器观测。运行前仍逐次人工批准；取消、心跳丢失或停止按钮锁定，需驱动断电后重连。窗口按钮通过独立串口种类及原子停止标志绕过模型和普通owner数据队列；完整帧仍须经过同一USB链路。

当前没有外部看门狗或复位默认失能硬件，C-STOP-003/004尚未验证。用户明确授权的例外仅限架空、在场、逐次审批台架；电脑/进程/ESP故障或USB失联仍须人工直接切断独立驱动电源。GPIO低读回不是轮子静止或独立停止链的证明，不宣称轮速、距离或角度已达到。

连接与退出均先确认驱动物理断电；没有断电声明，桥接拒绝关闭串口。窗口输入丢失时请求停止并保留串口；强杀进程无法由软件保证。密钥仍只在Mac进程内存。90%是PWM占空比，不是实测速度；可以在窗口把本次连接上限调为1..90，超过当前上限明确拒绝，不自动裁剪。

### 私有 USB 电机帧（v3 引入，v4 未改）

23..31依次为review、decision、observe、observed、settings、stop、power_off、heartbeat、state。原1..22编号不变，帧版本升为3，旧端拒收；Ayni ABI/schema不变。review/observe帧头id为permit，64字节负载 `<5Q2i4I>`：nonce、call、operation、attempt boot、attempt request、两路有符号PWM、duration_ms、当前cap、phase(1/2)、reserved0。decision/历史observed 48字节 `<5Q2I>`回送五个身份、approved(0/1)、reserved0。审批仅内存有效、不得存盘重用。当前设备不发送旧的observe帧，25/26编号保留给历史v3诊断端。settings为4字节cap；stop/power_off/heartbeat为空；state为有界JSON。Mac向Swift传递64位身份时使用十进制字符串及原始ticket十六进制，避免JSON浮点精度丢失。

HTTPS 保留证书验证，不跟随重定向，不读取环境代理，不自动重试。网络中断、取消或不完整响应不能证明远端未计费，结果按未知处理。超过正文上限或 token 截断明确失败，不静默截断。HTTP 状态可显示，原始 vendor 错误正文不输出。

官方模型接口依据：[DeepSeek 官方快速开始](https://api-docs.deepseek.com/quick_start/agent_integrations/)。实际联网结果单独记录，不能由离线夹具推定。

## 设备与旧固件恢复

只接受已验证 USB 身份：VID 1a86 / PID 55d3 / serial 5D01368694，端口 `/dev/cu.usbmodem5D013686941`。板型要求 16 MiB Flash / 8 MiB PSRAM。LCD 沿用 SCK12、SDI11、CS10、DC9、RESET8、RGB+INVON。没有启用旧录音、星图、Wi-Fi 或触摸服务。

使用原 IDF Python 执行 `device.py preflight`：保存旧 bootloader、分区表和整个 2 MiB 应用，确认当前应用与提供的旧固件一致，检查 `0x800000..0x1000000` 全部为 FF。它会重启板子，但不修改 Flash。不会读取 `demo_cfg` 凭据区。

`device.py deploy --variant motor` 只写分区表 sector `0x8000` 和应用 `0x410000`；保留原应用地址/容量，以及 audio 和 demo_cfg 分区。只在已确认空白的高 8 MiB 新增 Ayni LittleFS。Host 显式允许首次初始化完全空白卷，未知非空白介质仍拒绝并保留。

`device.py restore` 恢复保存的原分区表及原 2 MiB 应用，不写 bootloader、eFuse、demo_cfg、audio 或 Ayni 数据卷。恢复脚本不会自动运行。恢复资料位于被忽略的 `artifacts/recovery/`，不要清理该目录。

`device.py erase-volume` 只擦除 Ayni 数据卷 `0x800000..0x1000000`（升级到 schema 9 时需要），同样先核对 USB 身份；它删除旧日志和会话记录，不会自动运行。
